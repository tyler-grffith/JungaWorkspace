## Implemented decisions awaiting owner review

1. **First increment: library lifecycle.** Projects contain metadata, notes, a reference link, and selected tool types. Subsequent increments add working graphing and spreadsheet editors inside those projects.
2. **Organization.** One collection per project, plus favorites, archive, and recoverable trash. Deleting a collection keeps its projects. No permanent project deletion yet.
3. **Storage.** Save locally in the current browser at the current origin. Show this limitation in the interface; provide downloadable JSON backups and restoration. Accounts and synchronization are future work. Validate saved data and leave unreadable data untouched until an explicit replacement.
4. **Implementation.** React, TypeScript, and Vite; a small domain module separates project rules and persistence from the UI. Pinned dependencies and unit/browser checks support later agents and CI. Official references: https://react.dev/learn/creating-a-react-app and https://vite.dev/guide/.
5. **Initial design.** Quiet, light workspace with a persistent library sidebar, green accent, grid/list browsing, and a focused project overview. Desktop first, usable on narrow screens. User refinement pending.
6. **Examples.** Offer an optional LaPlace Intuition project with source link and notes. The graphing increment recreates its five functions as a native editable graph. Opening an older reference-only project with this exact source link initializes that example once; existing graph data and notes remain intact. Loading the example into a populated graph requires an explicit replacement action and supports undo. The larger aircraft graph and engineering workbook remain future references.
7. **Initial mathematics.** Use a small bounded numeric parser/evaluator for explicit functions of one variable. It supports arithmetic, named functions, forward references, constants, common math functions, and trailing domain restrictions. It executes no JavaScript. This covers the first example without embedding an external calculator or adding a large symbolic system. Formula length, nesting, dependency depth, entries, evaluations, and viewport ranges are bounded. Future capabilities may warrant replacing or extending this engine.
8. **Expression editing.** Begin with plain-text math and visible syntax help. Parameters have explicit slider/constant modes, finite bounds, and positive step sizes. Notes, colors, visibility, and on-curve labels are editable. Undo/redo is session-local with a 50-step history and grouped typing/slider changes; it is not persistent version history.
9. **Plotting.** Responsive SVG with adaptive numeric sampling, domain/pole breaks, pointer/keyboard pan and zoom, explicit bounds, and hover values. The plot is approximate: very narrow or rapidly oscillating features can be missed. Labels are attached near the right of each visible curve, with overlap refinement deferred to feedback.
10. **Tool persistence.** Optional, independently versioned graph and spreadsheet documents live on each project within the existing library format. Existing records remain valid. Save errors keep a draft and guard navigation. Removing a tool preserves its saved contents for re-enabling later. Library duplication copies both tools, while archive/trash retain them and trashed projects are read-only. Sequential cross-tab changes update the view; simultaneous editing remains outside this single-user prototype's guarantees.
11. **First spreadsheet scope.** One worksheet per project, initially 50 rows × 12 columns, growing to 200 × 26. A sparse cell model stores raw inputs and formatting, while calculated results are derived. This bounds rendering and makes a usable first grid reviewable. The 22-tab engineering reference requires later work on multiple sheets, custom functions, and larger grids; no import compatibility is claimed.
12. **Spreadsheet calculation.** A bounded parser/evaluator supports explicit arithmetic, A1 references/ranges, absolute/mixed references, common aggregate/logical/engineering functions, and visible errors for invalid, circular, or unsupported calculations. No JavaScript evaluation or external data calls. IF selects a branch lazily; IFERROR cannot hide circularity or resource limits. SUM/AVERAGE/MIN/MAX/COUNT use numeric values and ignore text/blanks/logical values. Exponentiation precedes unary minus. Dates, arrays, named/custom functions, and cross-sheet references are deferred. The formula dialect is an initial subset, not full Excel/Sheets compatibility.
13. **Spreadsheet editing.** Cells commit on Enter, Tab, or blur and cancel on Escape; pending edits warn on browser navigation. Arrow keys move and Shift extends selection. Tab moves right after editing and leaves the grid when not editing. Copy/paste uses tabular text externally and typed internal clipboard data to adjust relative references and preserve formats. Fill down/right copies the first row/column of a selection. Undo stores 50 session-local steps. Plain numbers and percentages recalculate independently of display formats; currency display is explicitly USD. Basic formatting and column sizing are included for practical small models.

14. **Backup restoration.** Accept native version-1 library JSON, including earlier downloads; optional export timestamps identify newer backups. Validate the entire file before writing, with a 10 MB upload limit. Default to restoring all projects and collections as independent copies, with collision-safe names and new collection mappings; preserve content, timestamps, favorites, and archive/trash status. Replacement preserves the snapshot's identities and requires explicit acknowledgment. Offer an unchanged download of current stored data, including unreadable data. Compare storage with the reviewed snapshot before a single write; changed previews must be refreshed. This protects sequential cross-tab changes, not truly simultaneous writes across independent tabs.
15. **Draft rescue.** Normal backup downloads overlay unsaved notes, graph documents, and spreadsheet documents/cell edits onto a readable library snapshot without marking them saved. Keep the last readable page state if storage becomes unreadable or a draft's project disappears. Raw-data downloads remain separate and unmodified. Restoration requires explicit disposal of any retained drafts and clears them only after a successful write. Project-details forms and calculator settings must be applied before they enter a backup. Backups remain manual; there is no automatic history or cloud copy.
16. **First tool integration.** A combined view places the existing spreadsheet beside its project graph. Named cells (up to 40, case-insensitive) resolve to ordinary cell references; cell sliders (up to 12) write numeric input cells. Graph point series (up to 8) pair equally sized one-dimensional x/y ranges in the same sheet, with optional lines and outline closure. Spreadsheet values remain authoritative: no copied coordinate cache or bidirectional formula dependency between engines. Invalid coordinates are omitted and break lines; equal axis scaling preserves geometry. The graph-only view also displays saved linked series. General graph expressions using sheet names and cross-project links are deferred.
17. **Integrated example and layout.** Recreate the exact six pairs from https://www.desmos.com/calculator/hnfguwahya with s/B2 = 5, h/B3 = SQRT(3)*s/2, and t/B4 = 0.323, limited to 0–1 with step 0.001. Coordinates occupy B7:C12, labeled with the original variable pairs; closure replaces the reference's repeated first row. Link settings can change names, sliders, and ranges. Compact headers and expandable formatting prioritize the table/plot in the combined view; narrower screens stack the panes. Pane resizing, point selection, slider animation, and shared undo remain follow-ups.

Use bounded numerical contour sampling, root refinement to reject poles/jumps, and a total operation budget. Equal axis scale applies when points or implicit geometry are present. Repeated roots, tiny features, and isolated roots remain sampling limitations; shaded inequalities remain deferred. Every row supports mouse/touch grips and Alt+arrow reordering, with undo and persistence. Replace color-name selects with visible named swatches.
19. **Playback and label editing.** Parameter animation uses elapsed time, a five-second full traversal at 1×, powers-of-two speed choices from 0.125× to 16×, and loop/reverse/once modes. Resume uses the current value and preserves reverse direction; replay after a one-way end starts at the minimum. Updates save at most ten times per second and group into an undo step. Graph edits, hidden tabs, save failures, or navigation stop playback; preferences and values persist, playing state does not. Spreadsheet cell-slider animation remains a separate follow-up. Labels store a world-coordinate anchor projected onto sampled curves plus size (8–36 px), fixed angle (15° steps), or screen-space tangent alignment. Drag commits once; arrows offer an alternative; double-click/Enter opens a nonmodal manager with Apply/Cancel. No automatic collision avoidance yet.

27. **Code as a module, not a project type (September 21, 2026).** Tyler clarified that "code project" means a project you create the way you create a graphing or spreadsheet project, holding files you write or import, with an output that runs them. `code` therefore became a third module id, so the project form, tool filter, cards, breadcrumbs and the `#/project/<id>/code` route follow from the existing registry. The earlier `projectType: 'code'` container stays for Cosmic Clock, relabelled "Bundled source project" in the form; both kinds may own outputs, and old libraries and backups keep loading unchanged. Files are one flat list whose paths carry their folders, bounded to 100 text files, 128 KB each and 512 KB per project, because the whole library shares one local-storage key. Binary assets, and therefore storage beyond local storage, remain a separate decision.

28. **Running a project without a server or a build step.** An output named `code-run` opens an HTML entry file from the project. Every other file becomes a `data:` URL and an import map redirects the project's own relative specifiers onto those URLs, so multi-file ES modules work with no bundler and no network round trip. `data:` rather than `blob:` is forced by the sandbox: the frame runs in an opaque origin and cannot read blob URLs minted by this document. Each module carries a `sourceURL` comment so failures name the project file. Transpilation (JSX/TypeScript), bare npm specifiers, and navigation between HTML files inside one output are not supported.

29. **Sandbox posture, to revisit with accounts.** The run frame uses `sandbox="allow-scripts"` without `allow-same-origin`, so project code cannot read the saved library, cookies, or the surrounding page — the opaque origin is the boundary that matters while everything is browser-local. Tyler chose to allow network access (CDN libraries, `fetch`) rather than confine the frame with a strict CSP, favoring functionality at this stage, and asked that security be revisited when user accounts are added. At that point, running another person's project becomes running untrusted code on a shared origin, and the tradeoff changes: expect to reconsider a CSP, a separate origin for outputs, and what a shared output may reach.

30. **Bundled files are viewable, not editable (September 21, 2026).** Working material shows the actual contents of the files it lists. Application source reaches the browser as raw text through a narrow `import.meta.glob`, lazily, one chunk per file; files under `public/` are fetched from their served URL so the viewer keeps working from a hosting subfolder. The viewer is read-only and says so: bundled material belongs to the application, not to the project, and the code module remains the place where files are owned and edited. Text over 120 KB is truncated with a note rather than rendered whole, because the time-zone boundary data is over a megabyte. Copying a bundled file into a code project, so it could be edited and run, is a separate decision.

31. **Copying bundled material into a code project.** Tyler asked for the file to be copyable, not only readable, so a viewable text file can be copied into an existing code project or into a new one started from that single file. The copy keeps the path below the scene root and is numbered rather than overwriting (`math-2.js`), so a copy never destroys work. Files a code project cannot store are refused with the reason rather than silently skipped, and the whole file is copied even when the preview was truncated. The bundled original stays read-only: copying moves a file from the application into a project the user owns, which is the boundary that keeps "what ships" and "what you are working on" distinct. Copying a file does not bring its imports with it; a copied module referencing `./math.js` will report the missing file when it runs.

32. **Solo-developer branch policy (September 21, 2026).** The required approving review on `main` was removed at Tyler's decision. It could never be satisfied: GitHub forbids self-approval, agents push as Tyler's account, so every pull request needed the administrator override to merge, and a control that is bypassed every time is worse than no control. What remains is what a solo developer actually benefits from — a current passing `Application checks` result, resolved conversations, and no force push or deletion of `main`. Requiring a status check also keeps direct pushes to `main` out, so work still arrives through a branch and a pull request. `CODEOWNERS` stays as routing rather than enforcement. Restore `required_pull_request_reviews` when a second person gains write access; `.github/main-protection.json` holds the policy to re-apply.

33. **The website vendors a build, not the source (September 21, 2026).** `tylergriffith.us` previously carried this repository as a git submodule, which served the _source_ tree: the browser was handed `.tsx` files it cannot execute and the app failed to load. The website repo now vendors the built `dist/` output under `JungaWorkspace/` as plain static files, and the live host updates by pulling that repo. This keeps the website with no build step and no toolchain, and it works because the build is already path-portable (`base: './'`, hash routes, decision 26). `scripts/deploy.sh` performs the copy in three separate stages — commit locally, push, go live — so the diff can be reviewed before anything is public, and it refuses to publish an unclean tree, a commit absent from `origin/main`, or a failing check. Deployment stays a decision rather than a trigger: CI does not deploy and a merge to `main` does not publish. The runbook is `docs/RELEASING.md`.

34. **Visual canvas: one document, four modes (September 23, 2026).** Tyler named the fourth module "visual canvas" and framed slides, frames, and diagrams as the same kind of thing that differs only in how it is organized and used afterwards. The document is therefore pages of positioned elements plus a `mode` — presentation deck, interactive mockup, diagram board, or simple animation — and the mode only changes page naming, which inspector sections appear, and how the presenter plays the pages. Changing mode never alters a drawing. `canvas` is a module id like the others, so the project form, filter, cards, overview panel, and `#/project/<id>/canvas` route follow from the registry; the shell gained one more explicit draft/editor branch, as `docs/ARCHITECTURE.md` anticipated for each new editor.

35. **Native SVG editor rather than an embedded canvas library.** Reviewed against embedding tldraw or Excalidraw: those deliver a working canvas quickly but their UI becomes the UI, and reshaping them to Tyler's design costs more than it saves once the module has to match the rest of the workspace, designer mode, and the bounded-engine philosophy. The editor is our own: an SVG stage, a flat z-ordered element list, groups as a shared id rather than nesting, and connectors that attach to elements at automatic or fixed anchor points. The same render components draw the editor stage, thumbnails, presenter, and SVG export, so what is exported is what is on screen.

36. **Gestures commit once; typed values commit on blur.** Drags (move, resize, rotate, endpoints, waypoints) mutate a transient copy and commit on release, so a gesture is one save and one 50-step undo entry, matching the graph's history model. Inspector number and text fields commit on blur or Enter for the same reason. Grid and snap toggles save without an undo entry because they are view preferences stored on the document.

37. **Images live in the document, bounded, until an asset store exists.** Images are downscaled to 1600 px on the long edge and stored as data URLs inside the canvas document, at most 600 KB each and 2.5 MB per document, because the whole library still shares one local-storage key (decision 27). Tyler's reference diagrams carry more image data than that, so a separate asset store (IndexedDB, with the backup format extended to carry it) is the next storage decision and is on the task list rather than built here.

38. **Presentation is an output; animation is keyframes; PDF is the print dialog.** Playing canvases uses the existing project-owned output route (`canvas-show`), read-only like code and scene outputs, plus a Present button in the editor that opens the same presenter. Animation stores keyframes (time, position, size, rotation, opacity) on elements and eases between them; this is the tween model Figma and Keynote use, chosen over scripted rules because it is drawable in the inspector without a language. PDF export prints one sheet per canvas at the canvas size in inches through the browser's own dialog, which yields a true vector PDF with no PDF library. PPTX and GIF export are deliberately later increments: both need a zip writer and an encoder the repository does not carry.

39. **draw.io import maps rather than emulates.** `.drawio` files (compressed or not) import as canvases with the common shapes, gradients, dashes, fonts, HTML labels (sub/superscripts become the canvas's `_{}`/`^{}` markup), groups and containers, edges with waypoints and arrowheads, and embedded images. Shapes without an equivalent become labelled rectangles and are counted in the import message rather than dropped, and an import that overflows a fresh page switches the document to an unbounded board. Full mxGraph fidelity is not a goal; getting Tyler's existing diagrams onto the canvas as editable elements is.

40. **Document: native contenteditable, parsed into blocks (September 24, 2026).** The Document module edits one contenteditable page natively and parses it back into a block model (paragraph, title, headings, list items with indent, quote, code, divider, image; runs with marks and safe links) on every change. The model is written into the page only when the document changes from outside, so the caret and the browser's own undo survive typing. Structural edits (headings, lists, indent, inserts) are small DOM operations of our own because Chrome's `formatBlock` and list commands leave empty paragraphs behind and nest lists into neighbours; inline formatting keeps using the browser's commands. Only the tags the renderer writes (and their browser aliases) survive parsing, so pasted HTML is reduced to the model's vocabulary and nothing else reaches storage. Font, size, and line spacing are document-wide; per-run fonts, tables, and pagination are later increments. Markdown in and out are pure functions, tested as a round trip.

41. **Document modules share one host (September 24, 2026).** With canvas, document, and collection all following the same shape — one versioned document on the project, one editor, one read-only output — the per-module wiring in `App.tsx` (draft state, route guards, backup overlay, editor branch, outputs panel, card art) became a registry. `src/modules/documents.ts` holds the storage side (validation, empty document, output factory) with no React; `src/modules/editors.tsx` holds the editor, outputs panel, output viewer, default document, and card art. `library.ts` saves and initializes any registered module generically (`saveModuleDocument`, `addModuleOutput`), `backup.ts` overlays drafts for all of them, `OutputPage.tsx` finds the viewer by output type, and `App.tsx` keeps one `moduleDrafts` map and one editor branch. Graph, sheet, and code keep their explicit wiring because their editors share state with each other (the linked workspace) and their props differ. A new module of this shape is now two registry entries plus its own folder; the 3D modeler and slicer prototypes will be added this way. This settles the architecture note that said to extract a host at three or four editors.

42. **Collections are a graph over a shared item pool.** A collection document is a pool of items plus collections that reference items and child collections by id, with several root collections allowed. A collection or item may have several parents (no copies); loops are refused by validation; unlinking from one parent keeps a thing another parent still holds and otherwise deletes it and the items only it held. Fields are declared per collection and stored per item, so one item can appear in collections with different templates. Presets seed fields, emoji, accent, and layout and are fully editable. Covers are `https` links or downscaled uploads (800 px, 200 KB), and a YouTube or YouTube Music link yields a cover from its video id without a fetch, because fetching page metadata from the browser is blocked by CORS. Export is Markdown for reading and JSON for re-import.

43. **Modeler and slicer as clickable prototypes on one workbench shell (September 24, 2026).** Tyler asked for SolidWorks and Bambu Studio recreations and accepted that the 3D rendering can wait; the priority is fully clickable placeholders that share human-centred design traits and streamline development across sub-apps. `src/workbench/` is therefore a declarative desktop-application shell (title bar, menus, command tabs with grouped tools, tree or settings panel, property panel with OK/Cancel, viewport with a view toolbar, right panel, status bar) rendered from a spec; each app is a spec plus a document and a command handler, so both share layout, interaction, and styling and differ in theme, accent, and content. Tools carry typed parameters, so a property panel is generated rather than hand-built. Features that need geometry stay visible but disabled or answer with a message saying what they await, so nothing pretends.

44. **Real history and settings, placeholder geometry.** The modeler saves a genuine feature history (sketches with plane, profile, and size; features with parameters; suppression) and derives its viewport by projecting each extrusion as a stacked box and each cut as a dashed box in isometric or orthographic views, so the FeatureManager tree, the picture, mass properties, and measure agree without a kernel. The slicer saves genuine printer, filament, process, and plate settings with box objects, and slices into a consistent estimate (time, mass, length, layers, cost) from volume and settings. A renderer, a sketcher, a kernel, mesh import, real slicing, and printer connectivity replace these stand-ins behind the same viewport slot and document shapes later. Both modules registered through the document-module registry (decision 41), which is what made them cheap to add.

45. **Revision pass: load modules lazily, write the library after typing pauses, let editors reach their siblings (September 24, 2026).** Tyler asked for a fresh, critical pass for speed and interconnection without losing functionality. Three structural changes came out of it. Module editors and output viewers are `React.lazy` imports behind one `ModuleLoading` fallback, so the library shell stops paying for every editor: the main bundle fell from 911 kB to 509 kB (gzip 275 → 157 kB) and each module arrives the first time one of its projects opens. Module edits no longer write the library on every keystroke: `useDeferredSave` holds the latest document, shows it as current, and commits once typing pauses for 400 ms, flushing synchronously before a route change, on `pagehide`, and on unmount, so nothing is lost and the per-keystroke cost is a state update instead of validating and stringifying the whole library. Editors still learn at once whether an edit is storable (validation runs synchronously; only the write is deferred). And `EditorProps` gained an optional `related` handle (the project's other document tools, with `get`, `save`, and `open`), provided by the host, so one module can hand work to another without knowing about storage. Smaller wins in the same pass: canvas text wrapping measures each word once and caches by font, page thumbnails are memoized, collection item counts are one pass over the graph, images paste into the canvas and the document from the clipboard, a canvas exports to the clipboard as PNG, and collection items may link to Junga projects (`#/project/<id>`), labelled "Junga".

46. **Real geometry for the modeler and slicer, without a kernel.** Tyler asked to add functionality to both prototypes. Rather than a third-party engine, `src/workbench/geometry.ts` is a small mesh layer: convex profiles (rectangle, circle, slot, hexagon) extrude and revolve on right-handed plane frames into triangle soups; meshes translate, rotate, mirror, flip, decimate, and report bounds and signed volume; binary and ASCII STL read and write; horizontal slicing chains loops, offsets walls, and hatches infill with even-odd clipping. There are no booleans: a cut or hole is a mesh with reversed winding, which signed volume and slicing both treat as a hole, and the viewport draws hollow. The modeler's `derive` rebuilds the part from its history (extrude with end conditions, revolve about the sketch centreline, cut, hole from the top face, mirror, linear pattern, reference planes; fillet, chamfer, and shell stay recorded and badged "awaits kernel"), so mass properties and measure are real; sketches carry an offset and position, defaulting to the top of the material. `src/workbench/Viewport3D.tsx` replaces the isometric SVG: an orthographic camera on a canvas with orbit, pan, zoom, fit, standard views, keyboard control, picking, ground-plane dragging, painter's sort, back-face culling, and hard-edge drawing (edges where faces meet at more than 20°), so a box shows twelve edges and a cylinder shows its rims. The slicer's objects may carry meshes (imported STL decimated to 4,000 triangles, or the part sent from the project's modeler through the `related` handle); `src/slicer/slicing.ts` slices the plate into layers of outer walls, inner walls, sparse infill (grid, triangles, honeycomb, gyroid, lightning as hatch families), solid infill on exposed surfaces, and brim, sums them into time, filament, and cost, draws them in Preview, and writes them as G-code. Supports are not generated and the printer stays simulated. Meshes are stored inside the slicer document (rounded to 0.01 mm, 2 MB cap) because the library still shares one local-storage key; the asset-store decision stands open.
